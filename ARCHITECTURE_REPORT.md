# Отчет о применении Clean Architecture в приложении для планирования и контроля освоения учебных материалов

## 3.1. Внутренний круг: Domain Layer (Модели и Бизнес-логика)

Это ядро системы, содержащее бизнес-логику. Оно делится на два ключевых компонента:

**Models (Бизнес-модели)** – это сущности предметной области, которые инкапсулируют самые общие и высокоуровневые правила. Они представляют собой простые классы Dart без каких-либо внешних зависимостей. Важно подчеркнуть, что на этом уровне мы говорим именно о бизнес-моделях (Entities), которые отражают концепции предметной области (например, "Задача", "Модуль обучения", "Учебная сессия", "Пользователь", "Настройки приложения"), а не структуру таблиц в БД. Пример такой структуры можно изучить на рисунке 3.

**Repository Interfaces (Интерфейсы репозиториев)** – абстрактные контракты, определяющие операции работы с данными на языке предметной области. Они не содержат реализации и не зависят от Flutter или технологий хранения. Каждый интерфейс репозитория инкапсулирует набор операций для работы с конкретной бизнес-сущностью (например, "Получить список задач", "Сохранить модуль обучения", "Добавить учебную сессию"). Пример такого интерфейса можно изучить на рисунке 4.

**AppCubit (Координатор бизнес-логики)** – класс, координирующий поток данных между Models и интерфейсами внешнего слоя, применяя бизнес-правила. Он зависит только от Entities и абстрактных интерфейсов репозиториев для получения данных. AppCubit инкапсулирует бизнес-операции приложения (например, "Добавить задачу", "Завершить модуль", "Запланировать сессию") и управляет состоянием приложения через паттерн Cubit из библиотеки flutter_bloc. Пример такого класса можно изучить на рисунке 5.

## 3.2. Внешние круги: Data Layer и Presentation Layer (Реализации и детали)

Внешние круги содержат конкретные реализации абстракций, ожидаемых ядром, а также все детали фреймворков.

**Data Layer (Слой данных)**: на этом этапе мы превращаем его из монолитного компонента в слой, который реализует интерфейсы репозиториев, определённые в Domain Layer. Этот слой представлен конкретными классами, которые напрямую реализуют эти интерфейсы, работая с локальным хранилищем (SharedPreferences). Важно, что эти классы знают все технические детали (SharedPreferences, JSON) и содержат Models для преобразования форматов хранения в бизнес-модели. Data Layer включает:

- **Models** – классы данных с JSON сериализацией, наследуются от Entities и добавляют методы `toJson()`/`fromJson()` для преобразования между форматом хранения и бизнес-моделями.
- **Data Sources** – конкретные источники данных (LocalStorageDataSource), работающие с локальным хранилищем через SharedPreferences.
- **Repository Implementations** – реализации интерфейсов из Domain Layer, координирующие работу с Data Sources и преобразующие Models в Entities.

Пример реализации Model структуры и класса Data Layer слоя можно рассмотреть на рисунках 6 и 7 соответственно.

**Presentation Layer (Слой представления)**: Этот слой также становится "плагином" к ядру. Он зависит от Entities и Repository Interfaces через AppCubit. Его ответственность – инициировать выполнение бизнес-операций (например, по нажатию кнопки) и отображать полученные Entities. Вся специфика Flutter (Widget, BuildContext, State Management через Cubit) содержится здесь.

**UI Layer (Слой пользовательского интерфейса)**: Экранные виджеты, организованные по бизнес-функциональности (Дашборд, Задачи, Модули, Расписание, Аналитика, Профиль, Настройки). Каждый экран использует BlocBuilder/BlocSelector для подписки на изменения состояния из AppCubit и отображения интерфейса.

Обновлённая структура проекта с учётом применения Clean Architecture изображена на рисунке 8.

Ключевое отличие от базовой трёхслойной архитектуры теперь очевидно:

- **Domain Layer совершенно чист**. Он не содержит даже намёка на Flutter или SharedPreferences. Вместо этого он определяет интерфейсы (interfaces), через которые будет получать данные (например, TasksRepository, ModulesRepository).

- **Data Layer не просто предоставляет данные, а является конкретной реализацией** (TasksRepositoryImpl, ModulesRepositoryImpl) этих доменных интерфейсов.

- **Направление зависимостей формализовано**: TasksRepositoryImpl (Data) → реализует → TasksRepository (Domain Interface). AppCubit (Presentation) зависит только от → TasksRepository (абстракция). TasksPage (UI) зависит от → AppCubit (Presentation).

Таким образом, Clean Architecture закрепляет статус Domain Layer как независимого, тестируемого и стабильного ядра приложения.

## 4. Реализация слоя Models

Реализация слоя моделей становится следующим шагом архитектурного развития, где основной упор делается на инкапсуляцию и контроль зависимостей. В рамках Clean Architecture модели находятся внутри Domain Layer как Entities, а в Data Layer существуют Models с JSON сериализацией. Такое решение связано с ключевой ролью бизнес-моделей: они служат центральным звеном, на которое опираются все остальные части приложения. AppCubit строит вокруг них свою логику, UI слой отображает их состояние, а Data слой обязан преобразовывать внешние данные именно в эти модели и обратно.

Выделение Models в отдельный слой преследует несколько стратегических целей:

- **Устранение циклических зависимостей**: В сложных проектах Domain Layer (с его Repository Interfaces) и Data Layer могут требовать взаимных ссылок. AppCubit зависит от Entity, а Data Source также зависит от Entity для преобразования. Расположение Entity внутри Domain и Model внутри Data создает четкое разделение ответственности, разрывая возможные связи, делая Entities общим, нейтральным фундаментом.

- **Чистота управления зависимостями (Dependency Management)**: В экосистеме Dart/Flutter управление зависимостями через pubspec.yaml является ключевым. Выделение Entities в Domain Layer и Models в Data Layer позволяет чётко контролировать, кто может на них ссылаться. Это предотвращает ситуацию, когда код UI или Data слоя по ошибке начинает импортировать и использовать элементы бизнес-логики напрямую, нарушая поток зависимостей.

- **Повышение переиспользуемости**: Бизнес-модели, представляющие основные концепции предметной области (Задача, Модуль обучения, Учебная сессия), зачастую стабильны и могут использоваться в нескольких независимых модулях или даже в разных приложениях внутри одной продуктовой экосистемы. Их изоляция упрощает такую миграцию и совместное использование.

- **Инкапсуляция источников данных**: Models и их преобразования должны быть полностью скрыты внутри конкретного DataSource. Это гарантирует, что специфика работы с конкретным хранилищем (SharedPreferences) не просачивается в другие части Data Layer. Каждый источник данных полностью отвечает за получение сырых данных, их парсинг в Models и преобразование в бизнес-модели (Entities).

Структура проекта с выделенным слоем Models можно увидеть на рисунке 9.

На схеме проекта можно увидеть классы, относящиеся к подслою models. Их ключевая идея заключается в том, что каждый DataSource полностью отвечает за свою "зону ответственности". Models являются реализационной деталью конкретного источника данных и преобразуются в Entities перед возвратом в Domain Layer. Это достигается путем расположения Models внутри подпапки data/models/.

Рассмотрим пример некой бизнес-сущности, Model и преобразование для локального источника на рисунках 10, 11 и 12 соответственно.

В чем же заключаются преимущества такого подхода:

- **Полная инкапсуляция**: Специфика работы с SharedPreferences (названия ключей, форматы JSON) остаётся внутри data/models/ и data/datasources/. Если формат хранения изменится, правки нужно будет делать только в этих директориях.

- **Отсутствие утечек абстракций**: Другие части приложения (например, Domain Layer или UI Layer) не знают о существовании TaskModel или деталях JSON сериализации. Они работают только с бизнес-моделями из domain/entities/.

- **Гибкость для разных источников**: Каждый DataSource может иметь свои собственные Models, оптимизированные под конкретный протокол или технологию. Например, будущий сетевой источник данных для REST API может использовать совершенно другие Models, не связанные с локальным хранилищем.

- **Упрощение тестирования**: DataSource можно тестировать изолированно, подменяя только Models, без необходимости создавать сложные JSON-структуры на уровне бизнес-моделей.

## 5. Применение архитектуры Repository

Архитектура Repository – это финальный шаг к созданию устойчивой и гибкой системы для управления данными. Ранее мы уже подготовили базовые бизнес-модели (domain/entities), определили интерфейсы репозиториев (domain/repositories) и вынесли работу с источниками данных в отдельные DataSource (data/datasources/). Но оставалась сложность: AppCubit продолжал напрямую зависеть от конкретных реализаций DataSource. Это мешало одновременному использованию нескольких источников и затрудняло внедрение сложных стратегий доступа к данным (таких как «сначала проверить кэш, потом запросить из сети»). Для полного понимания, рассмотрим, как развивался сам подход к организации доступа к данным:

- **Наивный подход**: AppCubit напрямую вызывал методы Storage, смешивая бизнес-логику с деталями хранения данных.

- **Clean Architecture**: AppCubit стал зависеть от абстрактного DataSource, но каждый компонент знал о конкретных источниках данных.

- **Repository Pattern**: AppCubit зависит от единой абстракции Repository, которая инкапсулирует ВСЕ источники данных и стратегии работы с ними.

Шаблон Repository решает описанную проблему, добавляя промежуточный уровень абстракции между бизнес-логикой (Domain Layer) и источниками данных (Data Layer). Repository становится единой точкой доступа к данным, полностью скрывая от бизнес-логики детали их получения — будь то локальное хранилище, сеть, память или их сочетание. Ключевая задача Repository — координировать работу нескольких источников данных, не усложняя бизнес-логику. В реальных приложениях данные почти всегда берутся из разных мест. Типичный сценарий включает:

- **Основной локальный источник** (SharedPreferences) для персистентного хранения данных.

- **Потенциальный сетевой источник** (REST API) для синхронизации данных между устройствами.

- **Промежуточный кэш в памяти** для быстрого повторного доступа.

Без Repository AppCubit должен был бы самостоятельно управлять этой сложностью, что приводило бы к дублированию кода и нарушению принципа единой ответственности.

Ключевое отличие от предыдущего подхода: AppCubit теперь ничего не знает о существовании разных источников данных. Он просто говорит: "Мне нужен список задач", а Repository решает, откуда его взять и как объединить данные, если это необходимо. Принцип схемы работы системы при внедрении паттерна Repository можно увидеть на рисунке 13.

## 6. Выполнение практической работы

### 6.1. Выбор архитектуры проекта

Учебный проект "Планирование и контроль освоения учебных материалов" переработан с применением Clean Architecture. Подход отделяет бизнес-правила от деталей реализации, повышая гибкость и поддерживаемость кода.

Характеристики проекта:

- **7 бизнес-экранов**: Дашборд, Задачи, Модули обучения, Расписание, Аналитика, Профиль, Настройки.

- **Данные**: используются SharedPreferences для локального хранения (без внешних API или БД).

- **Статус**: учебный, с потенциалом развития.

Несмотря на локальное хранение данных, проект оценен как средний по сложности из-за количества сущностей (задачи, модули обучения с темами и практиками, учебные сессии, профиль пользователя, настройки приложения) и разнообразия бизнес-логики. Clean Architecture оправдывает себя, закладывая масштабируемый фундамент на случай добавления реальной БД, интеграции с внешними API для синхронизации данных обучения, нового функционала или работы в команде.

### 6.2. Описание архитектуры для проекта

Проект построен на Clean Architecture с тремя основными слоями: Domain, Data и Presentation. Это обеспечивает разделение ответственности, низкую связанность и тестируемость.

**Domain Layer**

Ядро приложения с бизнес-логикой, независимое от Flutter и внешних сервисов:

- **entities** – Бизнес-модели (TaskEntity, ModuleEntity, StudySessionEntity, AuthUserEntity, AppSettingsEntity), независимые от Flutter и внешних зависимостей.

- **repositories** – Абстрактные интерфейсы репозиториев (TasksRepository, ModulesRepository, SessionsRepository, AuthRepository, SettingsRepository), определяющие контракты взаимодействия с данными на языке предметной области.

Принцип: Domain Layer задаёт правила предметной области и не зависит от технических деталей реализации.

**Data Layer**

Конкретные реализации абстракций Domain Layer:

- **models** – Data Transfer Objects с методами `toJson()`/`fromJson()` для преобразования между форматом хранения (JSON) и бизнес-моделями (TaskModel, ModuleModel, StudySessionModel, AuthUserModel).

- **datasources** – Источники данных (LocalStorageDataSource), работающие с SharedPreferences для локального хранения.

- **repositories** – Реализации интерфейсов из Domain Layer (TasksRepositoryImpl, ModulesRepositoryImpl, SessionsRepositoryImpl, AuthRepositoryImpl, SettingsRepositoryImpl), координирующие работу с Data Sources и преобразующие Models в Entities.

Принцип: Технические детали изолированы в Data Layer. Переход на БД или внешний API требует изменений только в этом слое.

**Presentation Layer**

Слой управления состоянием приложения:

- **bloc** – AppCubit и AppState для управления глобальным состоянием приложения с использованием паттерна Cubit из библиотеки flutter_bloc. AppCubit зависит только от интерфейсов репозиториев из Domain Layer.

**UI Layer**

Слой представления организован по бизнес-функциональности:

- **screens** – Экранные виджеты (home_page, tasks_page, modules_screen, schedule_page, analytics_page, profile_page, settings_page, auth/login_screen, auth/register_screen).

- **widgets** – Переиспользуемые UI-компоненты (task_tile, module_tile, modules_list_view, topic_row, profile_chip).

Принцип: UI не содержит бизнес-логики; она делегируется AppCubit из Presentation Layer, который использует репозитории из Domain Layer.

Такое разделение обеспечивает независимость слоёв, упрощает тестирование и позволяет изменять реализацию без влияния на бизнес-логику. Архитектура проекта представлена на рисунках 18, 19.

### 6.3. Реализация функциональности работы с задачами

В рамках применения Clean Architecture в приложении была полностью реализована функциональность работы с задачами – от описания бизнес-сущности до отображения данных на экране. Все остальные сущности приложения (модули обучения, учебные сессии, профиль пользователя, настройки, аутентификация) были реализованы по такому же принципу, в полном соответствии с архитектурными принципами.

#### 6.3.1. Слой Domain – Модель задачи

Класс TaskEntity, размещённый в директории lib/domain/entities/, представляет собой бизнес-сущность задачи. Модель содержит два поля: название задачи (title) и флаг выполнения (done). Класс не зависит от фреймворков и технологий хранения данных, отражая только бизнес-логику предметной области. Реализация показана на рисунке 20.

#### 6.3.2. Слой Domain – Интерфейс репозитория задач

Класс TasksRepository, размещённый в директории lib/domain/repositories/, представляет собой абстрактный интерфейс, определяющий контракт взаимодействия с данными о задачах на языке предметной области. Он не содержит реализации и не зависит ни от Flutter, ни от каких-либо технологий хранения – его единственная цель – декларировать, что система должна уметь делать: получать список задач и сохранять список задач. Реализация показана на рисунке 21.

#### 6.3.3. Слой Presentation – AppCubit для управления задачами

В классе AppCubit, размещённом в директории lib/presentation/bloc/, реализованы методы для работы с задачами:

- `addTask` – добавляет новую задачу через репозиторий.
- `toggleTask` – изменяет статус выполнения задачи через репозиторий.
- `deleteTask` – удаляет задачу через репозиторий.
- `clearDone` – удаляет все выполненные задачи через репозиторий.

Каждый метод инкапсулирует одну бизнес-операцию и зависит только от интерфейса репозитория, что обеспечивает независимость бизнес-логики от деталей реализации. Реализация показана на рисунках 22 - 25.

#### 6.3.4. Слой Data – Model задачи

Класс TaskModel, размещённый в директории lib/data/models/, представляет собой объект передачи данных для задачи. Model содержит те же поля, что и доменная модель (title, done), и наследуется от TaskEntity. Класс содержит методы `toJson()` и `fromJson()` для преобразования в JSON и обратно, что необходимо для работы с локальным хранилищем данных через SharedPreferences. Реализация показана на рисунке 26.

#### 6.3.5. Слой Data – Data Source задач

Класс LocalStorageDataSource, размещённый в директории lib/data/datasources/, представляет собой источник данных для работы с задачами. Он реализует хранение данных в SharedPreferences: получает список задач в формате JSON, десериализует их в TaskModel, и сохраняет обратно в JSON. Класс предоставляет методы `getTasks()` для получения списка задач и `setTasks()` для сохранения списка задач. Все операции синхронные для работы с локальным хранилищем. Реализация показана на рисунке 27.

#### 6.3.6. Слой Data – Реализация репозитория задач

Класс TasksRepositoryImpl, размещённый в директории lib/data/repositories/, представляет собой реализацию интерфейса TasksRepository из слоя Domain. Класс зависит от LocalStorageDataSource и использует TaskModel для преобразования данных. Он реализует все методы интерфейса репозитория, делегируя выполнение операций источнику данных и преобразуя Models в Entities перед возвратом в доменный слой. Реализация показана на рисунке 28.

#### 6.3.7. Слой Presentation – AppCubit состояния задач

Класс AppCubit, размещённый в директории lib/presentation/bloc/, содержит методы для управления состоянием задач с использованием паттерна Cubit из библиотеки flutter_bloc. Класс содержит состояние AppState, которое включает список задач (tasks). AppCubit использует репозитории из слоя Domain для выполнения бизнес-операций: загрузки задач, добавления задачи, изменения статуса задачи, удаления задачи и очистки выполненных задач. При выполнении операций он обновляет состояние через метод `emit()`. Реализация показана на рисунке 29.

#### 6.3.8. Слой UI – Экран задач

Класс TasksPage, размещённый в директории lib/screens/, представляет собой экран приложения для работы с задачами. Экран использует BlocBuilder для подписки на изменения состояния из AppCubit и отображения интерфейса. Экран содержит элементы управления для поиска задач, текстовое поле для ввода новой задачи, кнопку добавления задачи, список задач с возможностью отметки выполнения и удаления. При инициализации экран загружает текущее состояние через репозиторий, а при взаимодействии пользователя вызывает соответствующие методы AppCubit для обновления данных. ## Вывод

В ходе выполнения практической работы было спроектировано и реализовано кроссплатформенное мобильное приложение для планирования и контроля освоения учебных материалов с применением архитектурного подхода Clean Architecture. Это позволило разделить ответственность между слоями: Domain Layer содержит бизнес-модели (Entities) и абстрактные интерфейсы репозиториев, независимые от внешних деталей, Data Layer инкапсулирует работу с данными через конкретные реализации репозиториев и источники данных, а Presentation Layer и UI Layer отвечают за управление состоянием и взаимодействие с пользователем. Такой подход обеспечил тестируемость, поддерживаемость и масштабируемость кодовой базы.

Реализована модульная структура, организованная вокруг бизнес-сущностей (задачи, модули обучения, учебные сессии, профиль пользователя, настройки приложения), где каждый модуль включает полный стек компонентов – от моделей предметной области и интерфейсов репозиториев до экранов и виджетов. Управление состоянием построено на паттерне Cubit, что обеспечило реактивность интерфейса. Навигация реализована с помощью NavigationBar, что позволило создать удобную маршрутизацию между семью основными экранами приложения.

Несмотря на использование локального хранилища данных через SharedPreferences, архитектура проекта предусматривает переход к реальным источникам (REST API, базы данных) без изменения бизнес-логики. В результате создана полнофункциональная, структурированная основа для приложения планирования обучения, демонстрирующая применение современных принципов проектирования в экосистеме Flutter.
